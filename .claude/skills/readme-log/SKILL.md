# README 개발 일지 작성

## 대전제

`README.md`는 단순 기록이 아니라 **공모전 보고서의 원본**이다. 그래서 "무엇을 만들었다"가 아니라 **"무엇이 문제였고 왜 이렇게 풀었다"**로 쓴다. 심사위원이 읽는다고 생각하고 쓴다.

## 형식

최신 세션이 **맨 위**로 간다 (제목 바로 아래).

```markdown
---

# 🟢 8/02 — 한 줄로 이 세션의 성과

> 왜 이 작업을 했는지 한두 문장. 계기(멘토 피드백, 실측에서 발견한 문제 등)를 밝힌다.
> 구현물: `경로/파일.py`(역할 N줄) · `경로/파일2.py`(역할 N줄)
> 검증: 검사명 **N항목 0건** · 다른검사 **0건** · pyflakes **경고 0**

---

## A. 문제를 한 문장으로 요약한 소제목

**문제.** 무엇이 잘못돼 있었는지. 가능하면 실측 수치와 함께.

**해결.** 어떻게 고쳤고 **왜 그 방법인지**. 다른 선택지를 버린 이유도.

| 필요하면 | 표 |
|---|---|

---

## B. 다음 문제

...
```

## 규칙

1. **소제목이 문제를 말해야 한다.** "UI 개선" ✗ / "화면과 로직이 한 파일에 있어 판정을 안 건드렸다를 증명할 수 없었다" ✓
2. **검증 결과는 숫자로.** "테스트 통과" ✗ / "v1 결함 재발 35항목 0건" ✓
3. **실측 근거를 넣는다.** 판단의 근거가 된 측정값을 그대로 적는다 (예: "마지막 프레임 6점 중 5점이 y≈1.00").
4. **버린 것도 쓴다.** 무엇을 채택하지 않았고 왜인지가 설계 판단을 보여준다.
5. **파일 줄수를 정확히 적는다.** 추정하지 말고 실제로 센다:
   ```powershell
   (Get-Content 01_현행코드\console_ui.py).Count
   ```
6. **한계를 숨기지 않는다.** 레이더 물리 한계, 미해결 항목은 그대로 적는다. 안전 시스템 보고서에서 한계를 감추는 건 결함이다.

## 하지 말 것

- 실행하지 않은 검증을 "통과"로 적지 않는다.
- 없는 수치를 그럴듯하게 만들지 않는다.
- 과거 세션 항목을 소급 수정하지 않는다. 정정이 필요하면 새 세션에 정정 사실을 적는다.
- 이모지는 날짜 헤더의 🟢 외에는 쓰지 않는다.

## 마무리

일지를 쓴 뒤 이 세션의 결정 중 **다음 세션에도 유효한 것**이 있으면 `CLAUDE.md`에도 반영할지 사용자에게 확인한다. (예: 새 금지사항, 새 검증 절차, 확정된 설계 원칙)
