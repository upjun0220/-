## A. 시연 전 검증 — 관객 없이, 약 30분

여기서 하나라도 NG 면 시연에 들어가지 않는다.

### A-0. 기동 순서 (틀리면 파서가 죽는다)

1. 젯슨 재부팅
2. **레이더(IWR6843) 먼저 연결** — CLI `/dev/ttyUSB0`, DATA `/dev/ttyUSB1`
3. **약 5초 기다린 뒤** 차단기(CH340) 연결 — `/dev/ttyUSB2`
4. `ls /dev/ttyUSB*` 로 세 개가 위 순서대로 잡혔는지 확인

⚠ 차단기를 먼저 꽂으면 CH340 이 `ttyUSB0` 을 차지해 레이더가 밀리고 파서가 실패한다.
   USB 오류 `-32` / `-110` / `Errno 5` 가 뜨면 프로세스 재시작으로 복구되지 않는다.
   젯슨을 재부팅하고 2번부터 다시 한다.

5. 노트북·젯슨을 **휴대폰 핫스팟**에 연결. 학교 Wi-Fi 는 단말 간 통신이 차단된다
6. 젯슨 IP 확인 → 노트북 UI 기동 시 그 IP 를 쓴다
7. 50Ω·누설 모의 스위치가 모두 OFF인지 확인한다
8. 파워서플라이를 8V로 켜고 INA226 전압이 7.50V 이상인지 확인한 뒤 sender를 실행한다

⚠ 저장된 baseline이 있으면 sender가 즉시 LIVE로 진입할 수 있다. PSU가 꺼진 채 시작하면
`voltage_drop` 2회 연속 확인 후 약 1~2초 이내에 차단될 수 있다.

### A-1. 기동 로그 확인

젯슨 stdout 앞부분에서 아래 네 줄을 눈으로 본다.

| 확인할 줄 | 정상 |
|---|---|
| `[RF]` | `fall_classifier 로드 OK` |
| `[RF30]` | `용도분리 모델 로드 OK (window=30 ...)` |
| `DEVICE` | `cuda` |
| `[HAZARD]` | `Zone A = 'electric'` (또는 의도한 모드) |

`[RF30] 모델 없음` 이면 낙상 검출률이 크게 떨어진다. 배포를 다시 확인한다.

### A-2. 처리율 — 이번 시연의 최대 위험

입실 상태로 20초 두고 젯슨에서 측정한다.

```
for i in $(seq 1 20); do
  P=$(tail -c 300000 /home/project/stage1_filtered.json | grep -o '"frame_num":[ ]*[0-9]*' | tail -1 | grep -o '[0-9]*$')
  S=$(tail -1 /home/project/clf_decisions.jsonl | grep -o '"fnum_last":[ ]*[0-9]*' | grep -o '[0-9]*$')
  echo "$(date +%H:%M:%S) parser=$P sender=$S diff=$((P-S))"
  sleep 1
done
```

| 판정 | 기준 |
|---|---|
| **합격** | `diff` 가 증가하지 않고 0 근처 유지 |
| **불합격** | `diff` 가 계속 커진다 → 밀림 재발. 시연하면 경보가 갈수록 늦게 뜬다 |

`clf_decisions.jsonl` 최근 200건의 `dt` 중앙값도 본다. **0.063~0.08초** 여야 한다.
`dt` 최대값에 0.657초 스파이크가 있으면 Modbus 블로킹이 남은 것이다.

### A-3. 낙상 지연 — 60초로 시험한다

**입실 → 60초 대기 → 낙상.** 30초로 시험하면 의미가 없다.
지금까지 지연이 입실 시간에 비례해왔기 때문이다.

- 합격: 경보까지 **2초 이내**
- 낙상 실제 시각을 노트북 시계로 적어 화면 표의 `시각` 과 비교한다

### A-4. 동일 사고 중복 억제·복합 사고 병합

1. 낙상 경보를 띄운다
2. **'상황 종료'를 누르지 않은 채** 다시 낙상한다 → 동일 `fall_detected` 카드가 추가로 남발되지 않아야 정상
3. 같은 사건 중 서로 다른 전기 이상이 발생하면 기존 `ev_id`를 유지하고 `ev_types`에 병합되는지 확인
4. '상황 종료'를 누르고 다시 낙상 → 새 사건으로 정상 latch

⚠ 동일 유형은 중복 카드를 만들지 않고, 다른 유형은 조용히 버리지 않고 같은 사건에 병합하는 것이 현행 기준이다.

### A-5. 차단기 응답

`grep -c "BREAKER ERROR" <젯슨 로그>` 로 시연 구간 발생 건수를 센다.
0 이면 정상. 계속 뜨면 **화면 경보와 실제 차단이 다르다** — 시연 중
"차단 신호 발신 · 릴레이 응답 없음" 이 뜰 것이고, 그건 정직하게 설명한다.

### A-6. 차단 범위 실측 (8/20 확정 — 작업 대상 설비 회로 1개)

차단 상태에서 노트북 UI(또는 젯슨 패킷)의 INA226 표시가
**`0.000A` / 7.50~8.10V** 인지 확인한다. 로직 전원은 살아 있고(전압 정상),
부하 전류만 0이어야 한다 — 릴레이 CH0 밖(조명·비상등)까지 끊는 게 아니라는
실측 증거다. 값이 다르면 배선이 릴레이 앞단에 물린 것이다(§설계 ADR §7 참조).

## B. 시연 순서

```
시나리오 1. 낙상 — 경보·SOP, LED 유지
시나리오 2. 과전류 모의 — 설비 이상, 즉시 차단
시나리오 3. 과전류 차단+입실+무동작 5초 — 협착 Critical
```

### 시나리오 사이에 반드시

각 독립 시나리오 사이에서 **'상황 종료'를 누른다.** 차단기가 내려간 시나리오 뒤에는
원인 해소·3개 안전 확인 후 수동 재투입한다. 단, 하나의 사건 안에서 발생한 서로 다른
사고는 `ev_types`에 병합되어 함께 표시된다.

---

### 시나리오 1 — 낙상

| 단계 | 동작 | 화면에서 볼 것 |
|---|---|---|
| 1 | 입실 버튼 | 재실 상태 전환, 3D 에 점군 |
| 2 | ROI 안에서 자연스럽게 움직임 | 점군 추적 |
| 3 | **낙상** | **2초 이내 빨강 '낙상' critical** |
| 4 | — | 판단 근거 카드·낙상 SOP, **LED 점등·차단기 ON 유지** |
| 5 | '상황 종료' | 표에 종료 시각 기록. 전원 재투입 조작은 없음 |

**말할 것**
> 레이더 데이터를 젯슨이 판정하고, 노트북은 낙상 경보와 대응 SOP를 표시합니다.
> 낙상만으로는 설비 회로를 차단하지 않으며, 전기 이상이 확인된 경우에만 젯슨이 노트북과 독립적으로 차단합니다.

**근거 카드를 반드시 짚는다.** 이게 "그래프만 그리는 시스템" 과 갈리는 지점이다.

---

### 시나리오 2 — 과전류 모의·즉시 차단

| 단계 | 동작 | 화면·실물 |
|---|---|---|
| 1 | 퇴실 상태, LED 점등 확인 | 정상 설비 상태 |
| 2 | 50Ω 분기 스위치를 누름 | `설비 이상 · 과전류 Critical` |
| 3 | 차단 readback 확인 | LED OFF, `TRIPPED` |
| 4 | '상황 종료' 후 원인 해소·3개 안전 확인 | 수동 재투입 후 LED ON |

**말할 것**
> 본 시연은 LED와 50Ω 분기로 작업 대상 설비 회로의 과전류 상황을 모의합니다.
> 전기 이상은 재실 여부와 무관하게 즉시 차단하고, 재투입은 운영자가 원인 해소를 확인한 뒤에만 합니다.

---

### 시나리오 3 — 과전류 후 협착 Critical

| 단계 | 동작 | 화면·실물 |
|---|---|---|
| 1 | 입실 후 LED 점등 확인 | 재실 상태 |
| 2 | 50Ω 분기 스위치를 누름 | 과전류 Critical, LED OFF |
| 3 | 정지 상태 유지 | 차단 확인 즉시 무동작 타이머 시작 |
| 4 | 5초간 무동작 또는 포인트 소실 지속 | 같은 사건에 `협착 Critical` 병합 |

PINCH RF는 추가 90건 수집·사람 단위 검증 전이므로 이 시연에서 사용하지 않는다.

**말할 것**
> 과전류로 설비 이상을 먼저 확정하고 작업 대상 회로를 차단합니다.
> 그 뒤 입실 상태에서 5초 무동작 또는 포인트 소실이 지속되면 같은 사건을 협착 Critical로 확장합니다.

## C. 실패 시 대응

| 증상 | 원인 | 대응 |
|---|---|---|
| 낙상이 늦게 뜬다(5초 이상) | 프레임 밀림 재발 | sender 재시작. 재시작하면 백로그가 0 이 된다 |
| 낙상이 아예 안 뜬다 | 이전 경보가 latch 중 | **'상황 종료' 를 눌렀는지 확인.** 이게 가장 흔한 원인 |
| `[RF30] 모델 없음` | 배포 누락 | 젯슨 `~/fall_classifier_hybrid30.joblib` 존재 확인 |
| 3D 가 안 움직인다 | UDP 미수신 | 핫스팟 연결·방화벽 5005 확인. 젯슨 IP 재확인 |
| "차단 신호 발신 · 릴레이 응답 없음" | Modbus 무응답 | **정직하게 설명한다.** §D 참조 |
| 파서 실패 / USB 오류 | 연결 순서 | 젯슨 재부팅 → 레이더 먼저 → 5초 → 차단기 |

**시연 중 코드를 고치지 않는다.** 위 대응으로 안 되면 그 시나리오를 건너뛴다.

## D. 질문 대비 — 미리 준비한 답

**"낙상에 전원 끊는 건 과하지 않나요?"**
> 맞습니다. 낙상 자체는 전기 이상을 의미하지 않고, 무조건 차단하면 구조 작업에 필요한 설비에 영향을 줄 수 있습니다.
> 따라서 낙상은 즉시 경보와 SOP만 제공하고, 과전류·누설전류 같은 전기 이상이 별도로 확인될 때만 작업 대상 설비 회로를 차단합니다.

**"경보가 하나 떠 있으면 다른 사고는 안 뜨나요?"**
> 동일한 사고 유형은 중복 카드를 만들지 않지만, 과전류 후 협착이나 낙상처럼 서로 다른 사고는 같은 사건에 병합해 함께 표시합니다.
> 설비 이상이 먼저 발생했더라도 후속 인명사고를 무시하지 않습니다.

**"감전을 어떻게 검출하나요?"** (INA226 #2 실측 전)
> 이번 시연 범위에는 실제 누설전류 검출을 넣지 않았습니다. 저전류 병렬 분기를 사용할 경우에도 `누설전류 모의`라고 한정합니다.
> INA226 #2가 도착하면 공급 전류와 정상 귀환 전류의 차이를 반복 실측한 뒤 감전 판정 임계를 확정합니다.

**"과전류로 감전을 잡는 건가요?"**
> 아닙니다. 이번 과전류 분기는 협착 시나리오의 설비 이상을 모의합니다.
> 감전은 INA226 #2의 공급·귀환 전류 차이를 실측한 뒤 별도 누설전류 경로로 판정합니다.

**"차단기가 응답을 안 하는데요?"**
> 화면 경보와 실제 차단은 다른 사건이고, 그래서 따로 표시합니다.
> 지금 보이는 것은 판정이 정상이고 릴레이 통신이 미해결이라는 뜻입니다.
> 이걸 같은 것으로 보여주지 않는 것이 안전 시스템의 기본입니다.

**"차단까지 몇 초 걸리나요?"**
> 소프트 판단 → Modbus → 원격 분합은 **초 단위**입니다.
> 단락·누전 순시보호는 차단기 자체 하드웨어 몫이고, 저희 융합의 가치는
> **예지와 조기 경보**입니다. "0.1초 차단" 이라고 말하지 않습니다.

**"두 전기 이상을 동시에 구분하나요?"**
> 이번 단일 INA226 시연에서는 두 스위치를 동시에 누르지 않습니다. 전체 전류 증가량으로 저전류 이상 모의와 과전류 모의를 구분합니다.
> INA226 #2가 도착하면 공급·귀환 전류 차이를 별도로 검증합니다.

## E. 말하지 말 것

- "실제 감전을 검출합니다" → 센서 도착 전에는 성립하지 않는다
- "0.1초 안에 차단합니다" → 소프트 경로는 초 단위다
- "실배전의 지락과 토폴로지가 같습니다" → 왕복 불균형이 없어 과장이다
- "감전과 협착을 동시에 구분합니다" → 위치 오차가 구역보다 크다
- "낙상을 100% 잡습니다" → 젯슨 재학습본 재현율 70.0%, E 는 1/10 이다
- "낙상이면 자동으로 LED를 끕니다" → 현행 코드에서 낙상은 자동 차단 대상이 아니다
- "누설전류를 실제로 검출했습니다" → INA226 #2 공급·귀환 차이 실측 전에는 성립하지 않는다
