## 1. 네트워크 — 핫스팟으로 시작한다

**왜 핫스팟인가**: 유선 직결은 양쪽 고정 IP나 링크로컬 대기가 필요하고, 젯슨 설정을 COM13 시리얼로 해야 해서 마찰이 크다. 오늘은 **통신 성립을 최대한 빨리 확인하는 것**이 목표다.
**최종 시연은 유선으로 간다.** 공모전 현장 WiFi는 혼잡하다. 오늘 통신이 확인되면 유선도 이어서 붙여본다.

1. 노트북: 설정 → 네트워크 → **모바일 핫스팟** 켜기
2. 젯슨(COM13 시리얼 접속): 그 핫스팟에 WiFi 접속
3. 노트북에서 붙은 장치 IP 확인 — 핫스팟 설정 화면에 표시됨
   또는 `arp -a | Select-String "192.168.137"`
4. 양방향 확인
   ```powershell
   ping <젯슨IP>
   ```
   젯슨에서도 `ping 192.168.137.1`

**여기가 안 되면 그 위로 못 간다.** 코드 문제를 의심하기 전에 반드시 ping 부터 통과시킨다.

## 2. 순서 — 한 구간씩 연다

한 번에 다 켜지 말 것. 실패하면 어느 구간인지 못 가린다.

### 2-1. 노트북 단독 (젯슨 없이) — 기준선 확보
```powershell
# 창1
python 01_현행코드\sim_jetson.py
# 창2
python 01_현행코드\console_ui.py --live 127.0.0.1
```
UI가 정상 동작하면 **노트북 쪽은 무죄**다. 이후 문제는 전부 젯슨·네트워크 쪽.

### 2-2. 젯슨 단독 — 레이더가 읽히는가
젯슨에서 `jetson_sender.py`를 콘솔 출력만 보며 띄운다. 확인할 것:
- 레이더 시리얼이 열리는가 / `.cfg`가 로딩되는가
- 포인트가 들어오는가 (프레임당 점 수)
- `classify()`가 도는가 (torch 로딩 성공)

**⚠ `.cfg` 는 수정하지 않는다.** 포인트 부족은 각분해능 28° 병목이고 cfg 로 해결되지 않는다.

### 2-3. 연결 — 젯슨 → 노트북
```powershell
python 01_현행코드\console_ui.py --live <젯슨IP>
```
노트북이 HELLO(:5006)를 보내면 젯슨이 그 발신지로 회신하는 구조다. 젯슨에 노트북 IP를 하드코딩할 필요 없다.

**⚠ `--live` 에 넣는 것은 젯슨 IP다.** 노트북 자신(핫스팟이면 `192.168.137.1`)을 넣으면 안 된다.
수신 소켓은 `0.0.0.0:5005` 에 바인드하므로 **어느 IP에서 오든 받는다.** `--live` 값은 HELLO 를 **보낼 대상**으로만 쓰인다(`radar_core.py:275`). 이 값이 틀리면 젯슨이 회신을 시작하지 않는다.

**⚠ [8/03 확인] 설정 팝업의 '젯슨 IP' 입력란은 동작하지 않는다.** 현재 값을 표시만 하고 적용하는 코드가 없다(`SettingsPopup:1200`, 전수 검색 확인). **거기서 IP 를 고치지 말 것.** 바꾸려면 프로그램을 끄고 새 `--live` 값으로 다시 실행한다.

**연결 전 화면을 미리 보려면** 젯슨 없이:
```powershell
python 01_현행코드\console_ui.py --live 127.0.0.1
```
레이더 카드가 `연결 대기 / 장비 응답을 기다리는 중` 에 머문다(`console_ui.py:1507`). 젯슨이 살아나면 그 자리가 `연결됨 / 지연 ○○ms · 유실 ○건` 으로 바뀐다 — **이 전환이 §2-3 성공의 육안 신호다.**

**패킷이 안 들어오면 이 순서로 본다.**

| 증상 | 확인 |
|---|---|
| 화면이 계속 "연결 전" | 방화벽(§0-①) → ping → 젯슨 콘솔에 HELLO 수신 로그가 찍히는가 |
| 젯슨은 보낸다는데 안 들어옴 | 방화벽. `netsh advfirewall show allprofiles` 로 프로필 확인 |
| 들어오다 끊김 | 무선 혼잡. 유선으로 전환해 비교 |
| `schema_version` 경고 | 젯슨/노트북의 `radar_common.py` 가 다른 버전. **같은 파일이어야 한다** |

### 2-4. 전 과정 — READY → WARMUP → TRAIN → LIVE
UI에서 순서대로 눌러 진행한다. **이 흐름은 시뮬로만 돌려봤고 실기로는 처음이다.**
- WARMUP: 빈방 스캔 + 베이스라인 수집. 사람이 나가 있어야 한다
- TRAINING: LSTM-AE 학습 20~30초
- LIVE: 여기 진입해야 `prewarm()`이 돌아 SOP가 미리 만들어진다

### 2-5. 실제 동작 확인
낙상·진동 각 1회. 화면이 등급 색으로 바뀌는지, SOP가 뜨는지.

## 3. 확인해야 할 미지수 (오늘 답을 낸다)

> ⚠ 아래 5개 외에 `04_문서/화면_정보구조_확정_0803.md` §7 의 미확정 5건도 이날 실측으로 갈린다 (하드웨어 헬스 필드 추가 여부 / 렌더 갱신 구조 / stale 베일 / 경보 첫 프레임 지연 / prewarm).

- [ ] **`prewarm()`이 실제로 도는가.** jsonl 재생 때 LLM 응답에 약 1분이 걸렸다. 첫 호출의 모델 로딩 때문인지, prewarm 이 안 돈 것인지 갈라야 한다. LIVE 진입 후 상태 표시줄에 "AI 요약 사전 생성 완료"가 뜨는지 본다.
- [ ] **AE 이상점수가 `—`로 뜨는 게 정상인가.** 학습된 baseline 이 없으면 `—`가 정상이다. TRAINING 을 거치면 값이 나와야 한다.
- [ ] **10 Hz 실부하에서 화면이 끊기는가.** 정적 분석에서 잠재 위험 3건이 나와 있다(`DashboardPage.push()` 의 10 Hz `setStyleSheet`, `FacilityPlan` 250줄 paintEvent, `Track3D` GL). **끊김이 실제로 보일 때만** pyinstrument 로 측정한다. 안 보이면 손대지 않는다.
- [ ] **vib 패킷 시퀀스가 재생 데이터와 같은가.** 젯슨이 `ev.active` 를 언제 켜고 끄는지 실물로 확인한다.
- [ ] **젯슨 시계.** RTC 배터리가 없어 부팅마다 틀어진다. 화면의 경과시간이 음수나 이상값으로 나오지 않는지 본다(노트북 수신 시각 기준으로 계산하게 돼 있다).
