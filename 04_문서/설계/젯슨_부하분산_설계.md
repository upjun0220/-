> 목표: 실시간 안전 판정은 젯슨(엣지)에 남기고, 무거운 LLM·DB·대시보드는 별도 노트북(서버)으로 옮겨 부하를 분산한다.

# ⭐ 7/28 합의안 — 세 가지 안 종합

> 승원 안(젯슨=파싱만) · 민석 안(본 문서 원안) · 유빈 안(젯슨=전부, PC=화면만) 을 비교하고,
> 7/28에 확인된 신규 사실을 반영해 확정한 결론. **원안(2장 이하)은 그대로 유지하며, 아래는 그 위의 수정 사항이다.**

## A. 세 안의 차이는 사실 두 개뿐이다

젯슨에서 뺄 수 있는 후보는 렌더 / DB / LLM / 판정 넷이다.

| 뺄 대상 | 승원 안 | 민석 안(원안) | 유빈 안 | **합의** |
|---|---|---|---|---|
| 3D 렌더 | 뺌 | 뺌 | 뺌 | **논쟁 없음 → 뺀다** |
| pgvector DB | 뺌 | 뺌 | 조건부 | **논쟁 없음 → 뺀다** |
| LLM(Ollama) | 뺌 | 뺌 | 유지 | **노트북으로 이동 — 7/28 확정 (C절)** |
| **판정(classify·RF·AE)** | **뺌** | 유지 | 유지 | **젯슨에 유지 — 이동 불가** |

즉 실제 결정은 두 개였다. **판정을 옮길 것인가(→ 아니오), LLM을 옮길 것인가(→ 예, 7/28 확정).**

> **결론: 민석 안(원안)을 그대로 채택한다.** 승원 안에서는 구현 기법만, 유빈 안에서는 fail-safe 위 서사 논거만 취한다.

## B. 각 안 평가

### 승원 안 — 구현 방법은 채택, 경계선은 기각

`radar_parser.py`의 `out_f.write(json.dumps(rec)...)` 를 소켓 전송으로 교체하라는 **구현 기법은 정확하며 그대로 채택한다.**

다만 "젯슨은 파싱해서 쏴주기만" 하는 경계선은 다음 이유로 기각한다.

1. **낙상 판정이 네트워크 너머에서 일어난다.** 링크가 1초 끊기면 그 1초간 미검출. 안전 시스템 설계 결함.
2. **젯슨이 UART 읽고 JSON 만드는 일만 하면 라즈베리파이로 충분하다.** 심사에서 "40 TOPS 모듈을 시리얼 게이트웨이로 쓰는가"에 답이 없다.
3. **원본 포인트클라우드가 네트워크로 나간다** → "원본 미전송" 보안 서사가 붕괴.
4. 차단기까지 노트북이 제어하면 현장 액추에이터가 네트워크에 의존하게 된다.

### 민석 안(원안) — 골격으로 채택

세 안 중 유일하게 **fail-safe를 명시**했다(9장). 승원 안의 결함을 정확히 회피하며, "젯슨=현장 경비원 / 노트북=관제실 PC" 비유는 발표에 그대로 사용 가능. `frame_status`/`event` 메시지 규약(6장)도 실무적으로 충분하다. **본 문서 2~9장을 골격으로 확정한다.**

### 유빈 안 — LLM 유지 근거는 살리되 단독 채택은 보류

"젯슨의 가치는 보안이 아니라 현장 배치 가능성"이라는 논거와 "원본 미전송" 서사는 유효하다. 다만 8GB 메모리 여유가 미검증이므로 LLM 유지는 C절 측정 결과에 종속시킨다.

## C. 7/28 신규 사실 — 원안 작성 시점에 몰랐던 것

**1. 젯슨은 JetPack 7.2다.** 실측: `R39 (release)` / Ubuntu 24.04.4 / CUDA 13.2 / 드라이버 595.78. `nvidia-smi`는 `Orin (nvgpu)`를 정상 인식.

**2. 지금까지 "젯슨에서 LLM이 느리다"는 전제는 설정 오류였다.** ollama 프리빌트 CUDA 라이브러리에 `sm_87`(Orin 컴퓨트 능력)이 없어 CPU로 폴백하는 **NVIDIA 공식 인정 이슈**다. `/usr/local/lib/ollama/cuda_v13`가 이미 존재하므로 systemd 오버라이드 한 파일로 해결된다(D절).

**3. 따라서 노트북에 GPU가 없으면 LLM을 옮기는 것이 오히려 느려진다.**

| 위치 | 예상 속도 |
|---|---|
| 젯슨 CPU (현재) | ~2 tok/s (스왑 동반) |
| 젯슨 GPU (수정 후) | 20~25 tok/s |
| 노트북 CPU (GPU 없음) | 10~15 tok/s |
| 노트북 GPU | 30+ tok/s |

원안 10장의 "노트북 GPU 유무 확인"이 이 결정의 전제였음이 확인된 셈이다.

### C-1. GPU 활성화 결과 (7/28 실측)

**해결됨.** systemd 오버라이드로 `100% GPU` 전환 성공.

```ini
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment="OLLAMA_IGPU_ENABLE=1"
Environment="GGML_BACKEND_PATH=/usr/local/lib/ollama/cuda_v13/libggml-cuda.so"
Environment="LD_LIBRARY_PATH=/usr/local/lib/ollama/cuda_v13:/usr/local/lib/ollama:/usr/local/cuda/lib64"
Environment="OLLAMA_CONTEXT_LENGTH=4096"
```

| 항목 | Before (CPU) | After (GPU) |
|---|---|---|
| `ollama ps` PROCESSOR | `100% CPU` | **`100% GPU`** |
| 모델 점유 | 2.6 GB | **2.1 GB** |
| eval rate | **6.05 tok/s** | (측정 예정) |

> ⚠ `GGML_BACKEND_PATH`는 **디렉터리가 아니라 `.so` 파일 경로**여야 동작했다. `LD_LIBRARY_PATH` 동반 지정 필요.
> ⚠ 재부팅 후 CPU로 되돌아가는 사례가 포럼에 보고됨 → **재부팅 검증 필수.**

### C-2. 그럼에도 LLM을 노트북으로 옮기는 이유 (7/28 확정)

GPU는 **지연과 CPU 경합**을 해결하지만 **메모리는 1바이트도 줄이지 않는다**(통합메모리). 그리고 다음 세 가지 때문에 젯슨에 LLM을 두지 않기로 한다.

**1. 성장 여력.** 앞으로 젯슨에 추가될 것들이 이미 확정돼 있다.

| 예정 작업 | 메모리 영향 |
|---|---|
| RF 시계열 재학습 (19피처, 시퀀스 버퍼) | 증가 |
| 스마트 차단기 Modbus + 상태머신 | 증가 |
| 존 확장·클러터맵 정밀화 | 증가 |

LLM을 안고 있으면 여유가 1.5GB 남짓인데, **여유 1.5GB로 개발을 계속하는 것은 매 커밋마다 스왑 리스크를 안는 것**이다. 스왑에 빠지면 6 tok/s가 2 tok/s로 붕괴하는 것을 이미 실측했다(7/12 90초 타임아웃).

**2. 안전 시스템의 리소스 원칙.** 판정·차단은 최악 상황에서도 동작해야 하는 기능이다. 이를 "있으면 좋은" LLM과 같은 8GB를 놓고 경쟁시키지 않는다. (원안 4장·9장과 동일 논리)

**3. 디버깅 변수 제거.** RF 라이브 재학습(풍차 오탐)이 7/12부터 이월된 최우선 과제다. LLM이 젯슨에 없으면 "느려졌는데 LLM 때문인가 판정 때문인가"를 고민할 일이 사라진다.

### C-3. 그럼 GPU 작업은 헛수고인가 — 아니다

- **8/17 보고 자료**: "원인은 ollama 프리빌트 라이브러리에 Orin의 `sm_87`이 없어서였고 해결했다. **그럼에도** 판정 리소스 확보를 위해 LLM은 서버로 분리했다." → "안 돼서 옮겼다"가 아니라 "되는데도 옮겼다"는 서술이 된다.
- **폴백 경로**: 노트북 장애 시 `OLLAMA_URL` 한 줄로 젯슨 생성으로 되돌릴 수 있다.

### C-4. 노트북 이전으로 얻는 것  ⚠ **7/29 정정 — "모델 상향"은 폐기**

> **원안(취소선):** ~~젯슨 8GB 제약이 사라지므로 모델을 7~8B급으로 키울 수 있다.~~
> 7/29 노트북 실측 결과 **이 기대는 성립하지 않는다.** 아래 C-5 참조. 다만 **분리 결정 자체는 유효하다** — C-2에 명시했듯 이전 사유는 속도가 아니라 ①성장 여력 ②안전 원칙 ③디버깅 변수 제거이며, 셋 다 그대로다. 없어진 것은 부수 이득 하나뿐이다.

### C-5. 노트북 실측 (2026-07-29) — GPU 사실상 사용 불가

**실측.** `ollama run gemma2:2b --verbose` → **13.45 tok/s** (eval), load 16.5s. 젯슨 CPU 6.05 tok/s는 상회하나 GPU 가속은 전혀 없었다.

**원인 1 — 드라이버 미달.** Ollama는 NVIDIA 드라이버 **550 이상**을 요구하는데 본 노트북은 **452.56**(2020년, CUDA 11.0)이다. `server.log`에 `cuda`/`gpu` 관련 줄이 **한 줄도 없다** — 실패한 것이 아니라 탐지 대상에서 제외된 것. MX450 자체는 Turing(CC 7.5)이라 지원 목록 내에 있으므로 드라이버 상향으로 인식은 가능하다.

**원인 2 — VRAM 2GB (근본).** 드라이버를 올려도 여기서 막힌다.

| 항목 | 값 |
|---|---|
| GPU | NVIDIA GeForce MX450 (+ Intel Iris Xe 내장) |
| 총 VRAM | **2048 MiB** |
| 사용 중 (EasyConnect) | 119 MiB |
| 가용 | 약 1.9 GB |
| gemma2:2b GPU 점유 (젯슨 실측) | **2.1 GB** → **전체 적재 불가** |

→ 부분 오프로드로 13.45 → 25~30 tok/s 정도는 기대되나 **2배 수준이지 판갈이가 아니다.** 9B급 Q4(5GB대)는 부분 오프로드로도 불가, CPU 전용 시 3~4 tok/s로 L1 스트리밍이 성립하지 않는다.

**⚠ 벤치마크 해석 주의 — 위 숫자는 실제 워크로드가 아니다.** 450토큰 에세이 기준이다. 실제 산출물은 **L1 브리핑 2~3문장(약 80토큰), L2 근거 3줄 + 기각 후보 1줄**이다. 13.45 tok/s에서 80토큰 = **약 6초**, 스트리밍 시 첫 문장은 1초 내 표시된다. **경보 브리핑으로는 사용 가능하다.** `num_predict`를 실전 값(약 100)으로 캡 씌워 재측정한 숫자를 8/17 보고 앵커로 쓸 것.

**→ 진짜 병목은 속도가 아니라 한국어 품질이다.** gemma2:2b 출력에서 존재하지 않는 단어("피고사")가 반복되고, 재활을 "재생"으로 오역하며, 낙상 초동조치의 핵심인 *"환자를 함부로 움직이지 말 것"(척추 손상)* 이 누락됐다. L1/L2는 심사위원이 화면에서 직접 읽는 문장이므로 이 품질은 판정 성능 전체를 가린다.

**조치 순서**

| # | 조치 | 기대 |
|---|---|---|
| 1 | **`qwen2.5:3b-instruct-q4_K_M` 비교** (이미 설치돼 있음) | 동급 3B에서 한국어 우위. 최우선 |
| 2 | NVIDIA 드라이버 550+ 상향 → `ollama ps` PROCESSOR 재확인 | 부분 오프로드, 약 2배 |
| 3 | 실전 프롬프트 + `num_predict≈100` 재측정 | 8/17 보고 앵커 숫자 |
| 4 | **팀원 GPU 조사 (VRAM 6GB+ RTX 계열)** | **7~9B 한국어 품질을 원할 경우 유일한 경로.** 본 문서는 "노트북 서버"에 특정 기기를 지정한 바 없으며(3장), 같은 폐쇄망이면 팀원 기기도 무방 |

## D. 원안 대비 수정 3건

### 수정 1 — LLM 호출 위치를 환경변수로 뺀다 (폴백 확보용)

LLM은 **노트북에 둔다(C-2 확정)**. 다만 코드에 하드코딩하지 않고 환경변수로 분리해 폴백 경로를 남긴다.

현재 `radar_live_full.py`에 이미 다음 상수가 있다.

```python
OLLAMA_URL = 'http://localhost:11434/api/generate'
```

**이 한 줄이 곧 LLM의 물리적 위치다.** 다음과 같이 바꾼다.

```python
OLLAMA_URL = os.environ.get('OLLAMA_URL', 'http://localhost:11434/api/generate')
```

```bash
# 기본 — 노트북 생성 (확정 구성)
OLLAMA_URL=http://192.168.x.x:11434/api/generate python3 radar_live_full.py

# 폴백 — 노트북 장애 시 젯슨 자체 생성 (GPU 활성화 상태 유지)
python3 radar_live_full.py
```

→ 노트북이 죽어도 시연이 중단되지 않는다. 젯슨 GPU 설정(C-1)은 **폴백 자산으로 유지**한다.

### 수정 2 — Streamlit 대신 PyQtGraph  ✅ **7/29 확정**

원안 7장 4단계의 Streamlit 대시보드는 **실시간 3D에 부적합하다.** Streamlit은 스크립트 전체를 rerun하는 모델이라 10Hz 포인트클라우드 갱신에서 버벅이며, 지금 matplotlib에서 겪는 문제를 형태만 바꿔 반복하게 된다.

**확정: `breaker_facility_sim.py`(7/8 작성, PyQt5 + pyqtgraph, 젯슨 동작 확인 완료)를 노트북으로 가져와 관제 화면 뼈대로 쓴다.** 검증된 코드에서 출발할 수 있다.

#### 7/29 재검토 — "week5 Streamlit 재사용" 안을 검토했으나 기각

노트북에 week5 당시 구축분(Docker pgvector `radar-guard-db` · bge-m3 적재 완료 · `week5-2_pc.py` Streamlit)이 그대로 있어 재사용안이 제기되었다. **SOP 쪽은 재사용이 맞고, UI는 아니다.** 둘은 별개다 — pgvector는 프로세스 밖 Docker 컨테이너라 어떤 UI에서든 붙으므로, SOP 재사용은 UI 선택의 근거가 되지 않는다.

| 기각 사유 | 내용 |
|---|---|
| ① "이미 있어서 빠르다"는 착시 | `week5-2_pc.py` 42KB는 사이드바 버튼으로 **목데이터**를 띄우는 시나리오 데모다. 실시간 수신 구조가 없어 실제 재사용분은 RAG 호출부(503~514행)뿐이고 나머지는 전부 재작성 |
| ② ZeroMQ와 구조적 불일치 | rerun 모델이라 SUB 소켓을 `session_state`에 욱여넣거나 autorefresh 폴링해야 한다. 상시 수신 루프를 웹 요청 모델에 억지로 끼우는 것. PyQt는 `QThread` 수신 → signal → 위젯 갱신이 관제 SW 정석 |
| ③ **8/17 계획과 모순 (결정타)** | "사람 형태로 안 보인다"를 센서 물리 한계로 **데이터 정정 보고**하기로 했다. 정정하려면 개선된 3D(N프레임 누적 + 자세 프록시)를 실제로 띄워야 한다. 3D를 타협하는 선택지는 그 보고를 불가능하게 만든다 |
| ④ 부수 이득 | README 7/27 미해결의 "L4 입력창·스트리밍 텍스트가 matplotlib에서 껄끄럽다"가 `QLineEdit`/`QTextEdit`으로 함께 해소된다 |

#### 확정 구성

```
breaker_facility_sim.py (PyQt5 + pyqtgraph, 젯슨 동작 검증됨)
  └ QThread : ZeroMQ SUB 수신
  └ 좌 : 3D 트랙 뷰(5Hz, N프레임 누적 + 자세 프록시) + Facility Map
  └ 우 : L1 브리핑 / L2 근거 카드 / L3 SOP / L4 질의창   ← 화면의 주인공
  └ 하단 : 젯슨 상태 스트립
  └ RAG : week5-2_pc.py 503~514행 이식 (bge-m3 유지)
```

#### ⚠ 임베딩 모델 통일 — 놓치면 RAG만 조용히 깨진다

노트북 DB는 **bge-m3(1024차원)** 로 색인돼 있는데, 젯슨 `radar_live_full.py` 847행은 `OllamaEmbeddings(model='nomic-embed-text')`(**768차원**)이다. 쿼리와 색인의 임베딩이 다르면 "검색 품질이 나쁜" 것이 아니라 **차원 불일치로 실패한다.**

SOP DB가 노트북 확정이므로 **bge-m3로 통일**한다. `_rag_retrieve()`를 노트북으로 옮길 때 모델명도 함께 `bge-m3`로 변경할 것. → **F절 7번은 "이설·재적재"가 아니라 `docker start radar-guard-db` 후 검색 동작 확인으로 축소된다.**

## 0. 프로젝트 한 줄 요약 (처음 보는 사람용)

60GHz mmWave 레이더(IWR6843ISK-ODS)를 천장/프레임에 설치해 산업현장 작업자의 **낙상·정지형 이상(협착·감전)·설비 진동**을 비접촉 감지하고, 사고 시 **RAG 기반 조치 가이드(SOP) 안내 + 스마트 차단기 제어**까지 하는 온디바이스 AI 안전 에이전트. 현재 전체가 **Jetson Orin Nano 8GB** 한 대에서 동작한다.

---

## 1. 배경 — 왜 과부하가 나는가

Jetson Orin Nano 8GB는 **CPU와 GPU가 메모리를 공유**한다. 지금은 아래가 전부 이 한 대에 올라가 있다:

`레이더 수신 → 신호처리(LMS·DBSCAN·9D 피처) → LSTM-AE → 분류(규칙+RF) → Zone 경보 → pgvector DB → Ollama LLM(Gemma) → Streamlit 3D 렌더링`

이 중 **실제로 무거운 것은 3개**뿐이다:
1. **LLM (Gemma)** — GPU·메모리 큰 스파이크 (과거 llama3:8b는 OOM 프리징 유발)
2. **실시간 3D 렌더링** — GPU 점유, AI 추론과 경쟁
3. **DB (pgvector)**

반면 **레이더 판정 파이프라인(수신~분류~RF)은 매우 가볍다.** 문제는 무거운 셋과 가벼운 판정이 **같은 8GB·같은 GPU를 두고 경쟁**해, LLM이 뜨는 순간 메모리가 한계(실측 6.0GB / 7.485GB, 여유 1.5GB)에 붙고 렌더·추론이 서로 밀어내며 **프리징·프레임 지연**이 발생하는 것.

---

## 2. 해결 아이디어 — 2계층 분산

**"무거운 것을 젯슨에서 떼어 별도 노트북(서버)으로 옮기고, 젯슨은 가볍고 즉각적인 안전 판정에 집중한다."**

- **젯슨(엣지)**: 판단하고 즉시 조치(차단)까지. 네트워크 끊겨도 독립 동작.
- **노트북(서버)**: 매뉴얼 뽑고(LLM) 화면 보여주는(대시보드) 무거운 일. 실시간 아님(초 단위 허용).

> "서버"는 거창한 장비나 클라우드가 아니라 **같은 폐쇄망에 있는, 무거운 일을 대신 처리하는 컴퓨터**일 뿐. 개발용 노트북/PC 한 대면 된다.

---

## 3. 역할 분담

| 구분 | 젯슨(엣지) — 실시간 | 노트북(서버) — 무거운 처리 |
|---|---|---|
| 하는 일 | 레이더 수신 · 신호처리(LMS·DBSCAN·9D) · LSTM-AE · 분류(규칙+RF) · Zone 경보 · **차단기 제어** | **pgvector DB · Ollama(Gemma) LLM 생성 · Streamlit 관제 대시보드(3D 렌더)** |
| 성격 | 경량 · 저지연 · **네트워크 끊겨도 독립 동작** | 무겁지만 실시간 아님(초 단위 OK) |
| 왜 여기에? | 안전 판정은 즉시·독립이어야 함. 모델(AE·RF)이 작아 부담 거의 없음 | 과부하 원인(LLM·렌더·DB)을 젯슨에서 제거 |

### 노트북 서버 요구사항
- 젯슨과 **같은 폐쇄망**(공유기/핫스팟)에 연결
- **Docker(pgvector) + Ollama(Gemma2-2B, nomic-embed-text) + Streamlit** 구동
- 메모리 8~16GB. GPU 있으면 LLM 빠름(없어도 CPU로 Gemma2-2B 몇 초면 동작)
- 클라우드 불필요 → 폐쇄망이라 오프라인·보안 유지

---

## 4. 설계 원칙 — 왜 "판정"은 젯슨에 두는가 (중요)

안전 시스템이기 때문이다. **낙상·차단 같은 안전 판정이 네트워크 지연·단선에 영향받으면 안 된다.** 무거운 LLM은 몇 초 걸려도 되지만(이미 사전 생성·캐시), 판정은 즉시여야 한다. 즉 **"판정 = 엣지, 생성 = 서버"** 가 산업 안전 설계 원칙(엣지가 안전 제어, 서버가 무거운 분석)에 맞는다.

> 비유: 젯슨 = 현장 경비원(보자마자 즉시 판단·차단), 노트북 = 관제실 PC(상황판 + 매뉴얼 안내). 관제실 전화(네트워크)가 끊겨도 경비원은 자기 판단으로 즉시 조치한다.

**멘토 코멘트와의 조율**: 멘토님은 "젯슨은 LLM만 활용"이라 하셨다(판정을 서버로, LLM을 젯슨으로). 어느 쪽이든 과부하 원인(LLM·렌더)이 젯슨에서 빠지므로 목표는 같다. 다만 안전 관점에선 위 "판정=엣지"가 더 타당하다고 보고, **8/17 멘토링에서 최종 확정** 예정. (서버에 좋은 GPU가 있어 젯슨 GPU를 LLM 전용으로 쓰고 싶으면 스왑도 가능 — 코드 구조는 동일.)

---

## 5. 통신 방식

젯슨 ↔ 노트북은 폐쇄망에서 **가벼운 메시지만** 주고받는다.

- 추천: **ZeroMQ (pyzmq) PUB/SUB** — 라이브러리 하나, 별도 브로커 불필요. (익숙하면 MQTT/mosquitto도 가능)
- 젯슨 = 발행자(PUB): 상태·이벤트를 계속 송신
- 노트북 = 구독자(SUB): 받아서 대시보드에 표시
- 이 통로는 **"보여주기용"** — 끊겨도 젯슨의 판정·차단은 독립 수행(fail-safe)

## 6. 메시지 규약 (JSON, 데이터 인터페이스 명세서에 추가)

딱 두 종류만 정의한다.

### (a) frame_status — 매 프레임
```json
{
  "type": "frame_status",
  "ts": 1723000000.12,
  "step": "LIVE",
  "centroid_h": 1.07,
  "dop_std": 0.34,
  "zone_state": {"A": "NORMAL", "C": "PRE_ALERT"},
  "points": [[x, y, z], ...]   // 화면 표시용 캡 28점
}
```

### (b) event — 사고 확정 시
```json
{
  "type": "event",
  "ts": 1723000005.44,
  "event_type": "fall_detected",   // fall_detected | stationary_anomaly | vibration_anomaly
  "zone": "C",
  "severity": "critical",
  "situation": "Fall detected in Zone C"   // RAG 검색용 상황문
}
```

노트북은 `event`를 받으면 `situation`으로 **pgvector 검색 + Gemma SOP 생성** 후 대시보드에 표시한다.

## 7. 단계별 구현

**0단계 — 경계 확정**: 무엇이 젯슨에 남고 무엇이 노트북으로 가는지 목록으로 못 박는다(3장 표).

**1단계 — 통신 방식 결정**: ZeroMQ PUB/SUB 채택. 젯슨=PUB, 노트북=SUB.

**2단계 — 메시지 규약 정의**: frame_status / event (6장). 명세서에 추가.

**3단계 — 폐쇄망 구성**: 공유기/핫스팟에 둘 다 연결 → 고정 IP 확인 → `ping` 테스트 → 노트북 방화벽 포트(예: 5555) 오픈.

**4단계 — 노트북(서버) 구축**
1. Docker로 pgvector 띄우고 KOSHA SOP 재적재
2. Ollama 설치 + `ollama pull gemma2:2b`, `nomic-embed-text`
3. Streamlit 대시보드: frame_status로 3D 포인트·상태·그래프 렌더
4. 구독자(SUB) + RAG 핸들러: event 수신 → pgvector 검색 → Gemma SOP 생성 → 표시

**5단계 — 젯슨 경량화 (송신 전용)**: `radar_live_full.py`에서
1. matplotlib/Streamlit 렌더 코드 제거 → frame_status를 PUB로 송신
2. pgvector·Ollama 호출 제거 → event를 PUB로 송신
3. **판정·차단 로직은 그대로 유지**
4. `--headless` 실행

**6단계 — fail-safe & 통합 테스트**
- 노트북(서버)을 꺼도 젯슨이 낙상 감지·차단을 정상 수행하는지 (안전 핵심)
- 대시보드에 상태·SOP가 실시간으로 뜨는지
- 네트워크 끊었다 붙이면 자동 재연결되는지

**7단계 — 전/후 검증 (숫자로)**
- 젯슨 `sudo tegrastats`로 메모리 before/after 비교
- 사고 발생 → 대시보드 표시까지 end-to-end 지연 측정
- 프리징 없이 시나리오(낙상·정지형·차단) 리허설

## 8. 전/후 비교 (예상)

| 항목 | Before (단일 젯슨) | After (분산) |
|---|---|---|
| 젯슨 RAM | ~6.0GB / 7.485GB (여유 1.5, 위험) | ~2.5~3GB (여유 4.5+, 안정) |
| 프리징 | LLM/렌더 경쟁으로 발생 | 판정 전용이라 없음 |
| 판정 지연 | LLM 뜰 때 함께 지연 | LLM과 분리 → 항상 < 100ms |
| LLM 지연 | 젯슨에서 느림·메모리 압박 | 서버(가능하면 GPU)에서 처리, 판정 영향 0 |
| 안전성 | 무거운 작업이 판정을 막을 수 있음 | 판정·차단이 엣지에서 독립 동작 |

> "단일 기기 한계를 분산 구조로 극복"은 발표의 성과 포인트로도 활용 가능.

## 9. Fail-safe 원칙 (꼭 지킬 것)

- 서버·네트워크가 죽어도 **젯슨은 판정·차단을 독립 수행**한다.
- 서버는 "관제·안내" 역할일 뿐, 안전 조치의 필수 경로가 아니다.
- 재투입은 항상 사람 수동 확인(LOTO).
