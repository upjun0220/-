# 화면 정보구조 확정 — 2026-08-03(월)

> **범위**: 어느 화면에 무엇을 표시하고 무엇을 표시하지 않는가. **여기까지가 이 문서다.**
> **범위 밖**: 렌더링 구현(갱신 주기, paintEvent, 스타일 갱신 방식). 젯슨 10 Hz 실부하를 아직 못 봤으므로 확정할 수 없다.
> 근거는 전부 `01_현행코드/` 의 실제 코드 위치를 달았다. 코드에 없는 것은 "미구현"으로 적었다.

---

## 1. 무엇이 문제였나

`화면설계서 고도화 참고사항.md`(8/01 작성)는 **"현재 UI는 개발자 중심이니 User/Admin 화면으로 분리하겠다"** 는 개선 제안서다. 그런데 같은 날 진행된 UI v2 재설계에서 그 제안의 대부분이 이미 반영됐다.

그 결과 문서와 화면이 어긋났다.

- 발표 대본은 **"개편하겠습니다"** 라고 미래형으로 말하는데, 화면은 이미 그렇게 돼 있다. 심사에서 그대로 읽으면 **다 만든 것을 못 만든 것처럼 발표하게 된다.**
- 반대로 "무엇을 더 만들어야 하는가"의 목록이 없다. 남은 이틀에 무엇을 손댈지 판단할 근거가 없었다.

그래서 **"제안 대비 무엇이 이미 있고, 무엇이 정말 없는가"** 를 코드로 대조하는 것이 먼저였다.

## 3. 화면 축 결정 — 기능별 유지

**설계서는 "사용자별"(User / Admin) 축이고, 현행은 "기능별" 5메뉴다.** 축을 바꾸지 않기로 확정한다.

**근거**

1. **실질적으로 이미 분리돼 있다.** `DashboardPage` 는 평면도·구역 색·즉시 조치 위주(설계서의 User 화면 역할), `MonitorPage` 는 3D·계측 타일·판단 근거 위주(Admin 역할)다. 두 화면의 정보 밀도가 다르게 설계돼 있다.
2. **진짜 역할 분리는 로그인·권한 개념을 요구한다.** 8/17 멘토링까지 14일이고 젯슨 통합시험조차 아직 안 끝났다. 인증 계층을 새로 얹을 여유가 없다.
3. **심사가 영상 시연 우선이다.** 영상에서는 "화면이 두 벌 있다"가 아니라 **"경보가 뜨고 조치가 나온다"** 가 보여야 한다. 화면 수를 늘리면 촬영 분량만 늘고 핵심이 흐려진다.

**따라서 발표에서는 화면 구조를 새로 만들겠다고 말하지 않는다.** 이미 만든 것을 **"역할에 따라 정보 밀도를 다르게 설계했다"** 로 설명한다 (§6).

## 4. 화면별 정보구조 (확정)

좌측 네비게이션 6항목 — `SideNav.ITEMS:2005`

### [1] 대시보드 `DashboardPage:1285`
**질문: "지금 시설 전체가 정상인가, 사고는 어디서 났는가"**

| 표시 | 내용 |
|---|---|
| 장비 상태 카드 5장 | 레이더 / 판정 엔진 / 스마트 차단기 / SOP 데이터베이스 / AI 엔진 |
| 시설 평면도 | 구역별 색(감시 중·사전경보·경보·장비 미설치) + 작업자 위치, 클릭 시 감시 화면 진입 |
| 우측 요약 | 높이 · 움직임 · 포인트 · 이상도 4종, 최근 이벤트 4줄 |
| 근무 정보 | 근무조 · 담당자 · 설정 진입 |

- 장비 카드의 `detail` 에는 **근무자가 판단에 쓸 수 있는 것만** 쓴다. IP·포트·모델명·임계값은 [설정] 으로 보낸다 (1493행 주석).
- 구역 색은 700 ms 주기 `refresh()` 가 아니라 **패킷마다(10 Hz)** 갱신한다. 경보 1.5초 뒤 자동 전환(`AUTO_NAV_MS = 1500`, 2070행)이라 0.7초 지연이 그대로 보인다 (1430행 주석).

### [2] 실시간 감시 `MonitorPage:1549`
**질문: "무슨 일이 일어났고 지금 무엇을 누르는가"**

| 영역 | 내용 |
|---|---|
| 좌측 상단 | 포인트 클라우드 (3D ↔ 2D 측면도 전환) + 범례 3종 + 자세 캡션 |
| 좌측 하단 | 실시간 계측 타일 4칸 — 높이 / 움직임 / 포인트 / 이상도 |
| 우측 평시 | 히어로("이상 없음") · 구역 현황 · 감시 요약(마지막 수신 시각 포함) |
| 우측 경보 | 사고 종류·확신도 → 메시지 → 자동 차단 결과 → [조치 방법] → [확인함/상황 종료] |
| 상단 | 경보 배너 · 정지형 사전경보 줄 · 기준 미학습 안내 |
| 하단 | 타임라인 + 보조 도구 4개 |
| 우측 드로어 | `ActionDrawer:1193` — [조치 절차 SOP] / [판단 근거 Evidence] 2탭 |

**시선 순서를 고정한다** (1693행): ① 사고 종류·위험도 → ② 경과·확신도 → ③ 작업자 상태 → ④ 자동 차단 결과 → ⑤ 지금 누를 버튼.

**레이아웃 결정 2건은 실측으로 정해진 것이라 되돌리지 않는다.**
- 계측 타일은 우측이 아니라 **왼쪽 열 하단**. 우측에 두면 경보 시 4개 중 2개와 구역 현황이 스크롤 밖으로 밀렸다 (1624행 실측).
- 보조 도구 4개는 스크롤 **밖**. 우측 열 안에 두면 경보 패널이 밀어내 반쯤 잘렸다 (1781행 실측).

### [3] 이벤트 로그 `EventLogPage:1871`
시각 · 종류 · 구역 · 확신도 · 상태 5열, CSV 내보내기(UTF-8 BOM). 종료 처리는 초록으로 표시.

### [4] 현장 준비 `radar_core.PreparePage:1003`
빈방 스캔 12초(`SCAN_SEC`, 젯슨이 보낸 `cfg` 값을 쓰고 없으면 12.0) → 기준 수집 15초 → AE 학습 20~30초. **팝업이 아니라 전체 화면이다** — 1분짜리 '모드'이고 중간에 사람이 감지 구역을 나갔다 들어와야 한다 (1003행 주석). LIVE 되면 관제 화면으로 자동 복귀.

### [5] SOP 가이드 `SopGuidePage:1935`
경보 **전에** 미리 읽는 화면. 사고 유형별 즉시 조치 절차. **빨강을 쓰지 않는다** — 학습용이라 경보와 성격이 다르다.

### [6] 설정 `radar_core.SettingsPopup:1166`
탭 6개 — 연결 / 경보 / AI·SOP / SOP 관리 / **판정(읽기 전용)** / 진단.

**판정 탭이 읽기 전용인 이유는 UI 편의가 아니라 설계다** (1166행 docstring):
1. 실측 캘리브레이션 값이라 근무자가 슬라이더로 만질 성질이 아니다
2. 노트북에서 바꿀 수 있으면 "판정은 젯슨이 독립 수행"이라는 fail-safe 가 코드로 거짓이 된다
3. 사고 조사에서 "누가 언제 문턱을 바꿨나"가 추적 불가능해진다

### 팝업 6종 (모두 `radar_core.py`)
`SettingsPopup` / `EvidencePopup` / `PowerPopup` / `RestorePopup` / `QueryPopup`(L4 자유 질의) / `GraphPopup`(시계열 3종 + 임계선)

**팝업에 두는 기준**: 상시 감시에 필요 없고, 필요할 때 한 번 열어 보는 정보. `CLAUDE.md` §7-④ "버튼은 뒤로 뺀다"의 구현이다.

## 5. 표시하지 않기로 한 것 (근거 포함)

| 항목 | 이유 |
|---|---|
| FFT 스펙트럼 | 개발용 정보. 관제 근무자의 의사결정에 쓰이지 않는다 |
| SYSTEM HEALTH 상시 패널 | 같음. 장비 생사 여부는 대시보드 카드 5장이 이미 답한다 |
| 판정 임계값 편집 UI | §4-[6] 의 3가지 이유 |
| IP·포트·모델명·접속문자열 | 대시보드에서 [설정] 탭으로 이동 |
| 화면 설명 문구 | 관제 근무자는 읽지 않는다. 색과 위치로 말한다 (`CLAUDE.md` §7-③) |
| 데이터 없을 때의 추정값 | `—` 로 둔다. 관제 화면의 거짓 수치는 결함이다 (`CLAUDE.md` §4) |

**RED(`#EF4444`)는 위험 경보 외에 쓰지 않는다.** 색이 등급을 의미한다.

## 7. 미확정 — 젯슨 실측(8/05 수) 뒤에 결정

이 문서는 **정보 구조만** 확정한다. 아래는 실측 없이 결정할 수 없다.

1. **젯슨 하드웨어 헬스(CPU·메모리·온도) 추가 여부.** 추가하려면 `radar_common.py` 스키마에 필드를 넣어야 하는데 이 파일은 **젯슨과 노트북이 공유**한다. 한쪽 편의로 고치면 다른 쪽이 죽는다. 통합시험이 끝난 뒤 판단한다.
2. **렌더링 갱신 구조.** 잠재 위험 3건 — `DashboardPage.push()` 의 10 Hz `setStyleSheet`, `FacilityPlan` 250줄 `paintEvent`, `Track3D` GL 스톨. **끊김이 실제로 보일 때만** 측정한다.
3. **stale 베일 표시 시점.** 링크 다운 시 색은 정확하지만 `LINK_TIMEOUT`(3.0s) 전 구간엔 베일이 안 뜬다(1.8초 시점 실측 확인). 표시가 필요한지 판단 대기.
4. **경보 첫 프레임 `hide_shape` 지연.** `on_alert` 가 `_pump_state` 보다 먼저 계산돼 약 100 ms 어긋날 수 있다. 현 검증 스위트로는 재현 불가.
5. **LLM prewarm 트리거.** jsonl 재생 시 첫 응답 약 1분. 모델 로딩인지 prewarm 미실행인지 미확정.

## 8. 이 문서의 한계

- **코드를 읽어 정리한 것이지 화면을 눈으로 본 것이 아니다.** 8/01 스크린샷(`04_문서/UI_v2_스크린샷/`) 이후의 수정분은 렌더 결과를 확인하지 않았다.
- **젯슨 실데이터로 돌려본 화면이 아니다.** 모든 판단은 jsonl 재생·시뮬레이터 기준이다.
- 표의 코드 줄 번호는 **8/03 시점** 기준이다. 코드가 바뀌면 어긋난다.
