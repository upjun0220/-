## 무엇을 왜 바꿨나

### 1. 조치 가이드: 별도 OS 창 → 인앱 우측 드로어  ★ 가장 중요

v1 의 `SopPopup` 은 독립 최상위 윈도우였다. 듀얼모니터에서 다른 화면에 뜨거나 본 창 뒤로 숨을 수 있었고, 경보 중에 창을 찾아 헤매게 된다. 드로어는 부모 레이아웃 안에 있어 그럴 수 없다.

### 2. AI 요약을 SOP 하위로 강등 + 경고 문구

**v1 실측 화면에서 SOP 와 AI 요약이 서로 반대되는 지시를 동시에 띄우고 있었다.**

- SOP: "환자를 움직이지 마십시오 — 척추 손상 위험"
- AI: "작업자의 안전을 보호하는 방식으로 **움직여야 합니다**"

v2 는 순서를 `즉시 조치(확정) → 매뉴얼 원문 → AI 요약(참고)` 로 고정하고, AI 블록에 다음을 붙인다.

> **AI 요약 — 참고용. 위 [즉시 조치]와 다르면 즉시 조치를 따르십시오.**

### 3. 개발 정보 분리

### 4. 빨강의 역할을 셋으로 한정

① 활성 경보 배너 ② [조치 방법 보기] 버튼 ③ 차단된 구역.
**계측 수치는 경보 중에도 흰색을 유지한다.** 전부 빨개지면 시선의 종착점이 사라진다.
드로어의 [확인했습니다]도 빨강 → 시안으로 (확인은 위험한 조작이 아니다).

### 5. 2D 측면도 추가 (우측 상단 `2D 측면도 | 3D` 토글)

GPT 는 탑다운 평면도를 권했지만 **측면도로 갔다.**

IWR6843ISK-ODS 는 각분해능 약 28°. **수평(x·z)이 가장 부정확한 축**이고, 낙상 판정의 핵심 근거(`h_drop`, `height`)는 **수직축**이다. 탑다운은 제일 못 믿을 축을 크게 보여주고 결정적인 축을 버린다.

측면도는 `바닥 0m — 지금 0.57m — 서 있음 1.6m` 기준선이 그려져 있어 **그림 자체가 판정 근거**가 된다.
OpenGL 이 있으면 3D 가 기본, 없으면 2D 로 자동 대체된다.

### 6. 확신도 승격 / 포인트 수 강등

v1 은 대형 지표 4개가 높이·움직임·**포인트수**·이상도였고 확신도는 로그 한 줄에만 있었다.
→ 확신도는 경보 패널 상단 (`확신도 87%`), 포인트 수는 계측 타일로 유지하되 2개 이하면 주황 + `원시 · 누적 표시` 캡션.

### 7. 자동 차단 결과를 '실제 상태'로 표시

v1 은 경보 시 항상 "전원 차단 완료"라고 썼다. 차단기가 미연결이어도 완료라고 말한다.
v2 는 `breaker.state` 와 `power.src` 를 읽어 세 가지로 나눈다.

| 조건 | 표시 | 색 |
|---|---|---|
| 차단됨 + Modbus 실측 | `A 구역 전원 차단 완료 · 젯슨 자동 실행` | 초록 |
| 차단됨 + 모의값 | `A 구역 차단 신호 발신 (차단기 모의값 — 현장 차단 여부를 직접 확인하십시오)` | 주황 |
| 차단 안 됨 | `A 구역 전원 차단이 확인되지 않았습니다 — [전기 설비]에서 확인하십시오` | 빨강 |

### 8. 로그 출처 구분

젯슨 영문 원문과 앱 한글 문장이 같은 사건을 두 번 찍었다. 지우지 않고(감사 기록이다) `젯슨` / `앱` 태그를 달고 색을 낮췄다 → 중복이 아니라 '원문 + 해석'으로 읽힌다.

### 9. 네비게이션 잠금

미확인(UNACK) 경보 중에는 [실시간 감시] 외 메뉴가 비활성 + 사유 문구 표시.
v1 은 '다른 화면에 있으면 강제로 되돌리기'였는데, 눌렀는데 튕겨나가는 것보다 애초에 못 누르는 편이 예측 가능하다. (ACK 후 자동 해제)

### 10. 마지막 데이터 수신 시각 추가

GPT 가 지적한 항목인데 v1 어디에도 없었다. 우측 [감시 요약]에 `0.1초 전 · seq 1734` 로 표시. 링크 생존을 초록 점 하나가 아니라 숫자로 확인할 수 있다.

## 추가 작업 (8/01 오후)

### A. 구역 하드코딩 전면 정리 → 전부 `RADAR_ZONE`(A 변전실)

레이더 실물은 A 한 대뿐인데 여러 파일이 `'C'` 를 하드코딩하고 있었다. 그래서 루프백을 돌리면 **장비가 없는 C 구역에서 사람이 넘어지고, 정작 사람이 있는 A 는 '전원 투입'** 인 화면이 나왔다. (전력 복구 버튼이 이상하게 보인 것도 이것 때문 — 차단된 건 C 인데 화면의 A 는 멀쩡했다)

| 파일 | 위치 | 전 | 후 |
|---|---|---|---|
| `sim_jetson.py` | `ev_zone` 초기값 · 낙상 이벤트 · breaker · incidents · 로그 2곳 | `'C'` | `SIM_ZONE = RADAR_ZONE` |
| `jetson_sender.py` | `VIB_ZONE` (설비 진동 보고 구역) | `'C'` | `RADAR_ZONE` |
| `console_ui.py` | `ev.get('zone') or 'C'` | `'C'` | `RADAR_ZONE` |
| `console_ui.py` | `_DemoSource` 의 zone·zone_state·breaker | `'C'` 고정 | `ZONE_IDS` 순회 + `RADAR_ZONE` |

`VIB_ZONE` 은 특히 이상했다. 진동은 **이 레이더의 도플러(dop_std)로 재는 값**이라 물리적으로 레이더가 있는 구역의 값인데 C(조립)로 보고하고 있었고, `radar_common.EVENT_ZONE` 은 같은 `vibration_anomaly` 를 A 로 매핑하고 있었다 — **같은 사건이 경로에 따라 A 와 C 로 갈라져 보고**됐다.

> 실제 UDP 루프백으로 확인: `ev.zone=A` / `zone_state={'A':'ALERT'}` / `breaker={'A':'TRIPPED'}` / 배너 `낙상 · A 변전실 · 위험` / 차단 구역 `['A']` / 젯슨 로그 `ALERT Zone A: FALL DETECTED`.

### B. AI 요약에 레이더 실측값 주입 (`SopEngineV2`)

**문제** — v1 이 실제로 뱉던 문장:

> 1. 낙상 발생 장소를 확인하고 안전한 위치로 이동하세요.
> 2. 위험을 최소화하기 위해 작업자의 안전을 보호하는 방식으로 움직여야 합니다.
> 3. 사고 사유와 관련된 정보를 기록합니다.

레이더가 준 정보가 **한 글자도 안 들어갔다.** LLM 없이 하드코딩해도 똑같이 나오는 문장이라 "왜 LLM 을 넣었나"를 설명할 수 없었다.

**해결** — 젯슨이 계산해 보낸 `evidence` 를 프롬프트에 넣는다.

```
[감지 사실 — 레이더 실측값]
- 위치: A 변전실 (활선 고압 배전 설비가 있는 변전실)
- 사람 높이: 1.62 m → 0.31 m (총 1.37 m 하강)
- 쓰러진 뒤 움직임: 0.44 (거의 정지)
- 수평으로 퍼진 폭: 1.12 m
- 판정 확신도: 87%
- 해당 구역 전원: 차단 신호 발신(차단기 모의값 — 현장 확인 필요)

[참고 안전매뉴얼 발췌]
KOSHA GUIDE M-59-2012 …

위 [감지 사실]의 숫자와 장소를 반드시 인용해서 …
- [감지 사실]에 없는 수치를 지어내지 마라.
- 이미 차단된 전원을 다시 차단하라고 하지 마라.
- "안전하게", "적절히" 같은 막연한 말 대신 구체적 행동을 써라.
```

**숫자를 지어내지 못하게 하는 장치** — 프롬프트에 들어가는 값은 전부 젯슨 `classify()` 가 계산한 실측치다. LLM 은 주어진 숫자를 인용할 뿐 새로 만들 자리가 없다. 화면에서도 AI 블록은 `[즉시 조치](하드코딩) → [매뉴얼 원문] → [AI 요약(참고)]` 순서의 맨 아래이고 "다르면 즉시 조치를 따르십시오"가 붙는다.

**구조 변경 3가지**

1. **캐시 정책** — v1 은 `ev_type` 별로 요약문을 캐시했다. 이제 사건마다 수치가 다르므로 캐시하면 **틀린 숫자를 보여주게 된다** → 생성 결과는 캐시하지 않는다.
2. **`prewarm()` 의 역할 변경** — 요약문 사전 생성 → **모델 메모리 로드**(`num_predict=1`, `keep_alive=30m`). 지연의 실제 원인은 생성이 아니라 모델 로드였다.
3. **2단계 표시** — 매뉴얼 원문이 검색되면 먼저 띄우고(1~2초), AI 요약은 도착하는 대로 아래에 붙인다. LLM 을 기다리느라 매뉴얼이 안 보이는 일이 없다.

`console_ui.py` 의 `SopEngine` 은 **건드리지 않았다.** v2 에서 `SopEngineV2(core.SopEngine)` 로 상속해 검색 절차는 그대로 쓰고 생성만 바꿨다.

### C. 자동조치 문구 불일치 버그

경보 시 본 패널은 주황 "차단 신호 발신(모의값)", 드로어는 초록 "차단 완료" 로 **같은 사건을 두 가지로 말하고 있었다.** `on_event()` 에서 `_set_auto_action()`(실제 차단기 상태를 읽음)이 `show_for()`(기본 문구로 되돌림)보다 **먼저** 호출돼 덮어써진 것. 순서를 바꿨다.

## 경보 등급별 색 분리 (8/01)

`정상 초록 · 주의 주황 · 위험 빨강` 이 **화면 전체에서 같이** 움직인다 —
배너 · 배너 배경 · 경보 패널 테두리 · 조치 버튼 · 점군 · 인체 도식 · 머리 추정점 · 구역 카드 · 대시보드 칩 · 계측 라벨.

| 이벤트 | 등급 | 색 | 이유 |
|---|---|---|---|
| 낙상 · 감전 · 협착 · 과전류 · 전압강하 | critical | 빨강 | 게이트 통과 = **확정 사고** |
| 장시간 무동작 | warning | 주황 | 젯슨 라벨부터 `VERIFY: SHOCK/ENTRAPMENT` = **가서 확인해야 하는 사건** |
| 설비 이상 진동 | warning | 주황 | 사람 사고가 아니다 |

**소리는 끄지 않았다.** 정지형 이상은 감전·협착일 수 있어 조용히 넘어가면 안 된다. 대신 critical 은 매번, warning 은 4회에 한 번 울려 '지금 뛰어가' 와 '가서 확인' 을 귀로도 구분한다.

> ⚠⚠ **차단기와 무관하다.** `jetson_sender._latch_event()` 의 차단 조건은 `clf['severity']`(classify 반환값)이고, 정지형 2차 경보는 그 경로를 아예 타지 않는다. `radar_common.EVENT_SEV` 는 **표시 등급 전용**이라 이걸 바꿔도 차단 동작은 그대로다. 두 파일 모두에 이 경고를 코드 주석으로 박아 뒀다.

### 구역 색이 말하는 것

| 색 | 상태 | 조건 |
|---|---|---|
| 초록 | 감시 중 | 레이더 있음 + 링크 정상 + LIVE |
| 주황 (점선) | **사전경보** | 정지형 카운트다운 중 — 경보 아님 |
| 주황/빨강 (점멸) | 경보 | 등급색. 빨강만 점멸 |
| 회색 점선 | 장비 미설치 | 레이더 없음. 감시한다고 말하지 않는다 |
| 회색 실선 | 연결 대기 | 레이더는 있는데 링크 없음 |

### 경보 → 1.5초 → 자동 전환

구역이 붉어지는 걸 1.5초 보여준 뒤 감시 화면으로 넘어간다(`AUTO_NAV_MS`). '어디'를 먼저 인지시키고 상세로 가는 순서고, 시연 영상에서 맵이 붉어지는 장면을 쓸 수 있다.
⚠ **확인함(ACK) 이후에는 자동으로 끌고 오지 않는다** — 근무자가 이미 알고 있다.

### 정지형 PRE-ALERT — 젯슨이 보내고 있었는데 화면이 안 읽고 있었다

```python
STAT_PRE_SEC  = 10.0   # 1차: 정지 10초 → PRE-ALERT (경고, latch 안 함)
STAT_CRIT_SEC = 30.0   # 2차: 계속 무동작 → stationary_anomaly (latch)
```

젯슨은 그 20초 동안 매 패킷에 `"PRE-ALERT Zone A: no-motion 12s -- MOVE to cancel (18s to CRITICAL)"` 를 실어 보낸다. **`console_ui` 가 `pre_alert` 를 한 번도 읽지 않았다.** 사전경보의 존재 이유가 '움직이면 취소된다'인데 그 사실을 화면이 안 알려주면 의미가 없다.

→ `radar_common.parse_pre_alert()` 로 한 번만 파싱하고, **맵 구역 주황 + 감시 화면 주황 줄**에 `무동작 12초 · 18초 뒤 경보 — 움직이면 취소됩니다` 로 띄운다.
경보가 아니므로 **점멸·소리·네비 잠금 없음.** 움직이면 조용히 사라진다.
재생기에도 `PRE_SEC` 구간을 넣어 이 표시를 실제로 검증한다.

## ⚠ 실측 재생으로 드러난 센서 한계 3가지 (8/01 오후)

화면 문제인 줄 알았는데 **데이터·물리 문제**였다. 셋 다 코드에 근거를 박아 뒀다.

### ① PCA 자세 판정은 이 센서에서 성립하지 않는다 → 폐기

천장 하방 + 각분해능 28°. 2.3 m 아래 사람은 가로로 **1.5 m 번져** 보이고 반사는 머리·어깨 윗면에서만 온다. 즉 **서 있는 사람의 점군도 납작한 수평 원반**이라 PCA 주축이 항상 수평이다.

> 실측: **보행 중인데도 85.3 %가 `lying`** (normal 76.7 / wave 77.9 / fall 76.5 / still 98.3 / vib 88.5 %)

→ 자세를 **높이**로 판단한다. 젯슨 `classify` 가 `h_drop` 을 쓰는 것과 같은 근거다.
`머리 높이 ≥ 1.15 m` 서 있음 / `≤ 0.85 m` 누움 / 사이는 직전 유지.
수정 후 보행 **99.7 % standing**.

### ② 낙상 직후 점군은 사람이 아니다 (핵심)

정지한 사람은 도플러가 0 이라 FMCW 레이더가 놓친다. 그 자리를 **일정 거리 링**(다중경로·바닥반사)이 채운다.

```
낙상 마지막 프레임 6점:
  x+0.55 y1.00(h1.30)  x-0.46 y1.01(h1.29)  x-0.81 y1.00(h1.30)
  x+0.59 y0.99(h1.31)  x+0.57 y1.15(h1.15)  x-0.88 y1.43(h0.87)
```
5/6 점이 **y≈1.00 (거리 일정)** 인데 x·z 만 ±0.8 m 로 흩어졌다. 누운 사람이면 높이 0.1~0.4 m 여야 한다. 낙상 42건 전부 사후 높이가 **1.30~1.36 m 로 똑같이 고정**.

→ 사람 경보(낙상·정지형) 중에는 **형상을 그리지 않고** 이유를 쓴다:
`추적 소실 — 정지한 대상은 반사가 줄어 놓칩니다`
원시 점군과 수치는 그대로 보여 준다. **모르는 것을 그리지 않는 게 이 화면의 규칙이다.**

> 이건 UI 로 못 고친다. 프로젝트의 알려진 블로커(정지 대상 미검출)이고,
> 그래서 판정도 낙상 '순간' 의 `h_drop` 으로 하지 사후 상태로 하지 않는다.

### ③ 형상을 그려도 되는 조건 (실측으로 정한 값)

| 조건 | 값 | 근거 |
|---|---|---|

## 인체 도식 (스틱맨) — 캡슐 대체

낙상이 일어났는지 캡슐 두 개로는 안 읽혔다. 사람 모양으로 바꿨다.

### 무엇을 주장하고 무엇을 주장하지 않는가

| 주장한다 (전부 실측 계산값) | 주장하지 않는다 |
|---|---|
| 위치 (`center`) | **관절 각도** |
| 몸통 축 방향 (PCA 제1주성분) | **정면 방향** (축 중심 회전) |
| 축 방향 길이 (`length`) | 팔·다리 실제 위치 |
| 머리가 축의 어느 끝인지 | |

**팔다리는 고정 각도로만 그리고 절대 움직이지 않는다.** 프레임당 8점, 각분해능 28°로는 관절 측정이 물리적으로 불가능하다. 움직이는 스켈레톤은 측정이 아니라 애니메이션이 되고, "팔 각도는 어떻게 아셨어요?"에 답할 수 없게 된다.

화면 상단에 범례를 둔다 — `● 원시 점(누적)` / `● 머리 추정점` / `─ 인체 도식 · 관절 미측정`.

### 머리를 어떻게 찾나

센서가 천장 하방(nadir) 설치라 **y 가 작을수록 높고, 하방 레이더는 물체의 윗면을 본다** — 서 있는 사람이면 반사 대부분이 머리·어깨에서 온다. 그래서 **누적 점군 상위 15% 평균 = 머리**로 본다. (단일 최고점은 8점 노이즈에 통째로 흔들려서 못 쓴다)

**단, 이건 서 있을 때만 성립한다.** 누우면 머리·어깨·엉덩이 높이가 다 비슷해져 최고점 평균이 '몸통 한가운데'로 나온다.

| 자세 | 머리 위치 | 축 방향 |
|---|---|---|
| 서 있음 | 최고점 상위 15% 평균 (실측) | 그 방향으로 확정 + 기억 |
| 누움 | 몸통 축의 머리 쪽 **끝** | **넘어지기 직전 기억한 방향을 물고 감** |

### 겸사겸사 잡힌 것들

1. **PCA 축 부호가 매 프레임 뒤집혔다** — v1 은 축을 항상 위쪽(`UP`)으로 뒤집었는데, 누운 사람은 축이 수평이라 `UP` 과 거의 직교 → 부호가 무작위로 반전됐다(실측: 60프레임 중 5회). 캡슐이 미세하게 떨리던 원인. 이제 자세별 규칙 + 연속성 유지로 **120프레임 반전 0회.**
2. **도식의 발이 바닥에서 0.5 m 떠 있었다** — 점군 중심(centroid)에 대칭으로 걸었기 때문. 하방 레이더는 점군이 상반신에 치우쳐서 centroid 가 실제 몸 중심보다 위다. → **직접 측정한 머리에 앵커를 걸고 아래로 편다.** 서 있는 도식 발 높이 `+0.00 m`.
3. **서 있는 키를 PCA 길이로 잡으면 짧게 나온다** — 같은 이유. 서 있을 때는 `머리 높이 = 키`를 쓴다.
4. **측면도에서 누운 사람이 비스듬히 섰다** — 측면도는 깊이축(z)을 접으므로, 몸이 z 방향으로 누우면 투영 축의 x 성분이 0 에 가까워지고 정규화 과정에서 높이 성분이 지배한다(실측: 도식이 0.11~0.86 m 에 걸쳐 세워짐). → 측면도는 3D 축을 투영하지 않고 **자세로 축을 직접 잡는다.**
5. **측면도에서 누운 사람 팔이 공중 0.36 m 로 솟았다** — 누운 사람의 팔다리는 대부분 화면 안쪽으로 뻗는데 그 벌어짐이 전부 위아래로 그려진 것. `spread` 배율로 눌렀다.
6. **SOP 스레드 예외가 콘솔로 샜다** — ollama 미실행 시 앱 종료 중에 2차 예외까지 났다. 데몬 스레드는 무슨 일이 있어도 조용히 끝나게 감쌌다.

## 결정된 사항

- **3D 가 기본, 2D 측면도는 토글** — 시각적 임팩트 우선. 우측 상단 `2D 측면도 | 3D` 버튼으로 전환. OpenGL 이 없는 PC 에서는 자동으로 2D 로 대체되고 3D 버튼이 비활성된다.
- **모든 구역은 A 변전실** — 시연도 A 로 한다. 레이더를 늘릴 때 `radar_common.RADAR_ZONE` / `ZONE_EQUIPPED` 만 바꾸면 전 파일에 반영된다.

## 남은 판단거리

1. **`ollama` 로 실제 문장 품질 확인** — 프롬프트 구조는 검증했지만(가짜 응답으로 렌더까지 확인) gemma2:2b 가 실제로 숫자를 인용하는지는 `ollama serve` 켜고 봐야 안다. 안 되면 num_predict 를 줄이고 few-shot 예시 1개를 넣는 게 다음 수순.
2. **경보 시 LLM 생성 시간** — 노트북 CPU 13.45 tok/s 기준 220 토큰이면 약 16초. 매뉴얼 원문은 1~2초에 먼저 뜨므로 조치 자체는 안 막히지만, 심사 영상에서 AI 문장을 보여주려면 그 16초를 어떻게 편집할지 정해야 한다.
3. **`sim_jetson.py` MTU 초과** (위 참조).
