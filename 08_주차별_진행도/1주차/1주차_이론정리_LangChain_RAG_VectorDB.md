## 🎯 큰 그림: 우리 프로젝트에서 내 파트가 왜 필요한가?

### 시나리오 상상하기

> 변전소에서 작업자 A씨가 고압 설비 점검 중 갑자기 쓰러졌다. mmWave 레이더가 "낙상 감지!"라는 신호를 보낸다.
>
> 이때 시스템이 해야 할 일은?

1. **"낙상이면 어떻게 해야 하지?"** ← 산업안전매뉴얼(SOP) 수천 페이지 어딘가에 답이 있음
2. **"이 구역에서 취급하는 화학물질은?"** ← MSDS 문서 어딘가에 답이 있음
3. **"몇 초 안에"** 이 답들을 찾아서 → 현장 관리자에게 → "지금 당장 이렇게 하세요!" 가이드를 띄워줘야 함

이 "수천 페이지에서 0.1초 안에 정답 찾고, 사람이 읽기 좋게 정리해서 보여주는 시스템" 이게 바로 **RAG(검색 증강 생성)** 이고, 유빈이가 만들어야 할 부분이에요.

## 📚 PART 1. LLM이 뭐고, 왜 그냥 쓰면 안 될까?

### LLM (Large Language Model, 거대 언어 모델)
ChatGPT, Claude 같은 친구들. 사람처럼 글을 이해하고 답변해주는 AI.

### 그냥 ChatGPT한테 물어보면 안 돼요?

> 작업자: "변전소에서 사람이 쓰러졌어, 어떻게 해?"
> ChatGPT: "119에 신고하시고..."

문제점 3가지:

**문제 1) 우리 회사 매뉴얼을 모름**
- ChatGPT는 인터넷의 일반적인 지식만 학습함
- 우리 변전소의 SOP, 우리가 다루는 화학물질 MSDS는 학습한 적이 없음

**문제 2) 환각(Hallucination) - 그럴듯한 거짓말**
- LLM은 모르는 걸 "모른다"고 안 하고 그럴듯하게 지어냄
- 안전 매뉴얼에서 거짓말은 곧 인명사고

**문제 3) 최신 정보 반영 안 됨**
- 매뉴얼이 업데이트돼도 LLM은 모름

### 💡 그래서 등장한 게 RAG

> "LLM아, 답하기 전에 먼저 우리 회사 매뉴얼에서 관련 내용 찾아봐. 그거 보고 답해."

이게 RAG의 핵심 아이디어. **R**etrieval(검색) **A**ugmented(증강) **G**eneration(생성).

## 📚 PART 2. RAG가 어떻게 작동하는지 (실제 우리 시나리오)

### 작업자 낙상 시나리오로 따라가보기

```
[1단계: 사용자/시스템 입력]
"변전소 3구역에서 작업자 낙상 감지. 황산 취급 구역."

           ↓

[2단계: 검색(Retrieval)]
→ 우리 회사 매뉴얼 DB에서 "낙상 + 황산"과 가장 비슷한 문서 찾기
→ 찾은 것: 
   - SOP_낙상응급조치.pdf의 3페이지
   - MSDS_황산.pdf의 응급처치 항목
   - LOTO_절차서.pdf

           ↓

[3단계: 증강(Augmentation)]
LLM에게 보낼 프롬프트를 이렇게 조합:
"다음 매뉴얼 내용을 참고해서 답해줘:
[찾은 매뉴얼 내용 붙여넣기]
질문: 변전소 3구역 낙상 + 황산 취급. 어떻게 해야 해?"

           ↓

[4단계: 생성(Generation)]
LLM이 매뉴얼을 보고 답변 생성:
"1) 즉시 119 신고
 2) 황산 노출 가능성 → 작업자 만지기 전 보호장갑 착용
 3) LOTO 절차에 따라 3구역 차단기 OFF
 4) ..."
```

이 과정 전체를 코드로 짜면 길고 복잡한데, 이걸 **레고 블록처럼 조립**할 수 있게 도와주는 도구가 바로 **LangChain**이에요.

## 📚 PART 3. LangChain이란?

### 한 줄 정의
> **LLM을 활용한 앱을 만들 때 필요한 부품들을 연결해주는 프레임워크(레고 블록 세트)**

### 왜 필요해?

LLM 앱을 만들 때 해야 할 일이 너무 많아요:
- PDF 매뉴얼 읽어오기
- 텍스트를 잘게 쪼개기 (청킹)
- 텍스트를 벡터로 변환하기 (임베딩)
- 벡터 DB에 저장하기
- 사용자 질문이 오면 비슷한 거 찾기
- 찾은 거랑 질문을 합쳐서 LLM에게 보내기
- LLM 답변 받아서 사용자에게 보여주기

이걸 일일이 직접 코딩하면 며칠 걸려요. LangChain은 이 각 단계를 **이미 만들어진 함수**로 제공해서, 코드 몇 줄로 연결만 하면 되게 해줘요.

### 실제 코드 느낌 (아직 다 이해 못해도 OK)

```python
# LangChain 없이 RAG 짜면 100줄 이상...
# LangChain 쓰면:

from langchain.chains import RetrievalQA
from langchain.vectorstores import PGVector
from langchain.llms import OpenAI

# 1. 벡터 DB 연결
vectorstore = PGVector(connection_string="postgres://...")

# 2. RAG 체인 만들기
qa = RetrievalQA.from_chain_type(
    llm=OpenAI(),
    retriever=vectorstore.as_retriever()
)

# 3. 질문하기
answer = qa.run("낙상 사고 발생 시 대응 방법은?")
```

**핵심**: "검색하고 → LLM에 넣고 → 답 받는" 흐름을 LangChain의 `RetrievalQA`라는 블록 하나로 처리.

### 우리 프로젝트에서 LangChain의 역할

수행계획서에 정확히 나와 있는 부분:

> "**에이전트 워크플로우**: LangChain을 활용해 '위험 감지 → 지식 검색 → 대응 추론 → 관리자 보고'로 이어지는 의사결정 과정을 자동화"

이 4단계 워크플로우를 LangChain으로 엮어서 만드는 거예요.

## 📚 PART 4. 벡터 DB와 임베딩 (가장 어려운 개념, 천천히 가요)

### 문제 상황: "비슷한 문서를 어떻게 찾지?"

전통적인 검색 (Ctrl+F 같은 거):
- "낙상" 검색 → "낙상"이라는 글자가 들어간 문서만 찾음
- 그런데 매뉴얼에 "추락 사고"라고 써있으면? **못 찾음** ❌

우리가 원하는 건:
- "낙상" 검색 → "추락", "고소작업 중 떨어짐", "전도" 같이 **의미가 비슷한** 문서까지 찾기

### 해결책: 임베딩(Embedding)

**임베딩** = 글자를 **숫자 벡터(좌표)** 로 바꾸는 것

```
"낙상"        → [0.21, -0.45, 0.83, ..., 0.12]  (1536차원 숫자)
"추락"        → [0.19, -0.43, 0.81, ..., 0.11]  (위와 매우 비슷한 좌표)
"점심메뉴"     → [-0.91, 0.22, -0.05, ..., 0.67] (완전 다른 좌표)
```

핵심 마법:
- **의미가 비슷한 단어/문장은 좌표가 가깝다**
- 의미가 다른 건 좌표가 멀다

### 벡터 DB는 이 좌표들을 저장하고, 가까운 좌표를 빠르게 찾아주는 DB

비유:
- 일반 DB(MySQL 등) = "이름이 정확히 '홍길동'인 사람 찾아줘"
- 벡터 DB(pgvector 등) = "이 좌표 [0.21, -0.45, ...]랑 가까운 거 찾아줘"

### pgvector가 뭐냐?
- PostgreSQL이라는 일반 DB에 **벡터 검색 기능을 추가한 확장**
- 즉, 일반 데이터(작업자 이름, 사고 시간 등)와 벡터(매뉴얼 임베딩) 를 **한 DB에서 같이 관리** 가능
- 이래서 우리가 1주차에 `pgvector/pgvector:pg16` 이미지를 Docker로 띄운 거예요!

### 우리 프로젝트에서의 흐름

```
[프로젝트 시작 전 1회 작업: 매뉴얼을 DB에 저장]
SOP/MSDS PDF 수십 개 
   → 작은 단락으로 쪼개기 (Chunking)
   → 각 단락을 OpenAI 임베딩 API로 벡터로 변환
   → pgvector에 저장
   
[운영 중 매번 발생: 사고 발생 시]
"변전소 3구역 낙상 감지" 
   → 이 문장도 벡터로 변환
   → pgvector에서 가까운 벡터(=비슷한 매뉴얼 단락) Top-5 가져오기
   → LLM에게 전달
```

## 📚 PART 5. Docker는 왜 쓰는가?

### 문제 상황 (Docker 없을 때)

PostgreSQL을 컴퓨터에 설치하려면:
1. PostgreSQL 16 설치 파일 다운
2. 설치 마법사 따라가기 (포트 설정, 비밀번호 설정...)
3. pgvector 확장 별도로 컴파일해서 설치
4. 환경변수 설정
5. 설치 끝나면 OS 어딘가에 영구적으로 남음
6. **버전 업그레이드, 삭제, 재설치 = 지옥**

팀원이랑 협업하면 더 지옥:
- "내 컴퓨터에선 잘 되는데?" → Windows/Mac/Linux마다 다름
- "PostgreSQL 13 깔았어요" "저는 16인데..." → 버전 충돌
- 젯슨 보드에 똑같이 깔아야 함 → 또 헤맴

### Docker의 해결책

> **앱과 그 환경 전체를 "컨테이너"라는 박스에 통째로 넣어서 어디서나 똑같이 실행**

비유: Docker 이미지 = **냉동도시락**
- 박스 안에 OS, PostgreSQL 16, pgvector, 설정까지 다 들어있음
- 어떤 컴퓨터(Windows, Mac, Linux, 젯슨)에서도 데우면(`docker run`) 똑같이 작동
- 안 쓰면 통째로 삭제(`docker rm`) → 컴퓨터 깨끗

### 우리가 1주차에 한 명령의 의미

```powershell
docker run -d --name radar-guard-db -p 5432:5432 -e POSTGRES_PASSWORD=... pgvector/pgvector:pg16
```

해석:
- `docker run`: 컨테이너 실행
- `-d`: 백그라운드로 (터미널 안 잡고)
- `--name radar-guard-db`: 이 컨테이너 이름
- `-p 5432:5432`: 컴퓨터의 5432포트 ↔ 컨테이너의 5432포트 연결
- `-e POSTGRES_PASSWORD=...`: 비밀번호 환경변수 설정
- `pgvector/pgvector:pg16`: Docker Hub에서 이 이미지 가져와서 실행

### 우리 프로젝트에서 Docker가 더 중요한 이유

수행계획서에 보면:
> "엣지 AI 연산 인프라: Jetson Orin Nano를 기반으로 ... **로컬 PostgreSQL 서버 운영**"

**최종 목표**는 개발 PC가 아니라 **젯슨 오린 나노**(작은 ARM 임베디드 보드)에서 DB를 돌리는 거예요. 
- 개발 PC(x86 윈도우)에서 만든 환경을 → 젯슨(ARM 리눅스)에 그대로 옮겨야 함
- Docker 없으면 일일이 재설치
- Docker 있으면 → 같은 이미지 그대로 `docker run` → 끝

## 📚 PART 6. PowerShell은 왜 쓰는가?

### PowerShell = Windows의 "고급 명령 프롬프트"

옛날 cmd(검은 창)의 강력한 후속작. Linux 터미널처럼 강력한 스크립팅 가능.

### 왜 GUI(클릭) 안 쓰고 PowerShell(타이핑)?

**이유 1) Docker는 본질적으로 명령줄 도구**
- Docker Desktop GUI도 있지만, 옵션 다 못 줌
- `-e POSTGRES_PASSWORD=...` 같은 환경변수, 볼륨 마운트 등은 명령어가 정확
- 팀원과 공유할 때도 명령어 한 줄로 끝 ("이 명령 그대로 쳐봐")

**이유 2) 재현성(Reproducibility)**
- GUI는 클릭 순서를 글로 설명해야 함 → 길고 헷갈림
- 명령어는 복붙 = 누가 해도 똑같이 작동

**이유 3) 자동화의 시작**
- 나중에 "DB 띄우기 + 데이터 백업 + 로그 확인" 같은 걸 스크립트(.ps1) 한 파일로 만들 수 있음
- GUI로는 못 함

### 다른 곳에 적용하기

이 사고방식은 어디든 통해요:
- AI 모델 배포 → Docker + 명령줄
- 웹 서버 운영 → Docker + 명령줄  
- 데이터 분석 환경 구성 → Docker + 명령줄
- "어디서든 똑같이 돌아가는 환경"이 필요하면 → 무조건 Docker

## 🎯 1주차 실습 의미 총정리

### 유빈이가 한 일 = "RAG 시스템의 토대 만들기"

```
[1주차 실습] Docker로 pgvector PostgreSQL 띄우기 ✅ 완료
    ↓
[앞으로 할 일]
- 산업안전매뉴얼(SOP) PDF 수집
- LangChain으로 PDF 읽고 청킹
- OpenAI 임베딩으로 벡터화
- pgvector에 저장
- LangChain RetrievalQA로 검색+생성 파이프라인 구성
- LLM 답변을 관제 대시보드에 표시
```

### 다른 사람한테 1주차 설명할 때 쓸 한 줄

> "산업 안전 매뉴얼 수천 페이지에서 사고 상황에 맞는 대응책을 즉시 찾아주려면, 글의 '의미'를 검색할 수 있는 벡터 DB가 필요해요. 그래서 PostgreSQL에 벡터 검색 기능을 추가한 pgvector를 Docker 컨테이너로 띄웠습니다. Docker를 쓴 이유는 나중에 젯슨 오린 나노 임베디드 보드에 똑같은 환경을 그대로 옮기기 위해서예요."

이 한 단락만 외워도 1주차 이론은 다 설명 가능해요.
